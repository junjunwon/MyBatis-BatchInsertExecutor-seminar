01 문제 정의

OOM의 진짜 원인은
무엇인가

❌ 잘못된 가설

"엑셀 row 수가 많아서 OOM이 난다"

대부분의 첫 번째 생각. chunking이 이미 들어가 있어서 "chunk로 잘랐으니 안전하다"고 착각하기 쉽다.

✓ 실제 원인

"MyBatis가 배치 중간 상태를 메모리에 얼마나 오래 붙잡고 있느냐"

SIMPLE 모드에서 chunk로 잘라도, 각 chunk의 SQL payload가 크면 순간 피크 메모리는 여전히 높다.

실제로 검증해야 할 질문
  • 메모리를 가장 오래 점유한 객체는 무엇인가
  • SIMPLE과 BATCH의 메모리 차이는 어디서 발생하는가
  • flushStatements()를 언제 호출해야 피크가 줄어드는가
  • useGeneratedKeys가 왜 설계를 제한하는가
📸 SCREENSHOT GUIDE #1
실제 활용 예시 이미지 삽입
아래 이미지를 사용합니다. 필요하면 발표 직전에 OOM 로그 화면으로 교체해도 됩니다.
02 코드 구조 해부

핵심 흐름

ExecutorType executorType = useGeneratedKeys ? ExecutorType.SIMPLE // generated key 필요 : ExecutorType.BATCH; // 대량 insert 효율 List<List<T>> batches = chunked(items, batchSize); for (List<T> batch : batches) { try (SqlSession s = factory.openSession(executorType)) { M mapper = s.getMapper(mapperClass); insertFn.accept(mapper, batch); if (executorType == ExecutorType.BATCH) { s.flushStatements(); // batch 버퍼 실행 s.clearCache(); // local cache 정리 } } // auto close }

03 BatchExecutor 내부

누적의 시작점은
doUpdate()다

⚠️ 흔한 오해 "flushStatements()에서부터 batch가 시작된다"
→ 틀렸다. 누적은 mapper.insert() 호출 시점, 즉 BatchExecutor.doUpdate()에서 이미 시작된다.
public int doUpdate(MappedStatement ms, Object param) { StatementHandler handler = newStatementHandler(...); String sql = handler.getBoundSql().getSql(); if (sql.equals(currentSql)) { // 같은 SQL → 기존 Statement 재사용 batchResult.addParameterObject(param); // 누적! } else { // 다른 SQL → 새 Statement 생성 statementList.add(stmt); batchResultList.add(new BatchResult(ms, sql)); } handler.batch(stmt); // JDBC batch 등록 (아직 DB X) return BATCH_UPDATE_RETURN_VALUE; }
BatchExecutor가 보유하는 상태
statementList
JDBC Statement 목록
batchResultList
row별 parameter 객체 참조 누적
currentSql / currentStatement
SQL 비교용 상태
메모리 피크의 핵심
row 수가 커질수록 세션 안에 아래가 동시에 쌓인다:
• flush 전 JDBC statement
• row별 parameter object 참조
• SQL 템플릿 + key generator 처리 정보
04 API 역할 분리

flush · clearCache · close
역할이 다르다

flushStatements()

  • Statement.executeBatch() 실행
  • generated key 후처리
  • statement.close()
  • statementList.clear()
  • batchResultList.clear()
⚠️ commit이 아님. 트랜잭션 확정은 별도.

clearCache()

  • localCache.clear()
  • localOutputParameterCache.clear()
batch statement 버퍼를 직접 비우지 않음.
BATCH 메모리 핵심은 flushStatements().

session.close()

  • transaction.close()
  • deferredLoads = null
  • localCache = null
  • 세션 생명주기 완전 종료
try-with-resources를 쓰는 이유.
@Override public List<BatchResult> doFlushStatements(boolean isRollback) throws SQLException { // executeBatch → key 처리 → closeStatement → 리스트 clear ... stmt.executeBatch(); closeStatement(stmt); currentSql = null; statementList.clear(); batchResultList.clear(); }
@Override public List<BatchResult> doFlushStatements(boolean isRollback) { return Collections.emptyList(); }
execute vs commit — 자주 헷갈리는 포인트
execute
SQL을 JDBC/DB에 보내
실제 insert/update를 수행하는 시점
commit
이미 실행된 변경 내용을
최종 확정하는 시점
→ 하나의 트랜잭션 안에서도 SQL은 여러 번 실행될 수 있고, commit은 마지막에 한 번만 일어날 수 있다.
05 전략 비교

SIMPLE vs BATCH

구분 SIMPLE BATCH
SQL 실행 시점 mapper 호출 즉시 flushStatements() 시점
메모리 위험 단일 SQL payload 피크 누적 buffer 피크
flushStatements() no-op (emptyList 반환) 핵심 정리 포인트
useGeneratedKeys 지원 제약 있음
OOM 한계 결정 요인 총 row 수 chunkSize × payload
현재 코드 분기 주문 헤더 insert 주문 아이템 insert
30,000건 기준 실측 비교
ExecutorType.SIMPLE ~3.4 GB
ExecutorType.BATCH ~390 MB
※ 현재 SQL shape(AES_ENCRYPT, foreach multi-row) 기준 추정치. JVM heap 설정에 따라 달라질 수 있음.
-Xmx=1024MB 기준 추정 안전 건수
SIMPLE: 약 6,000건 (116KB/row)
BATCH: 약 55,000건 (13KB/row)
→ 같은 30,000건이라도 결과가 다른 이유
06 현재 Mapper 분석

왜 이 mapper가
특히 무거운가

ExcelOrderCustomerMapper.xml — insertExcelOrdersBatch
<!-- 세 가지 무거운 요소가 동시에 존재 --> <insert useGeneratedKeys="true" keyProperty="id"> INSERT INTO order_customer VALUES <foreach collection="list" ...> ( AES_ENCRYPT(#{buyer_name}, ...), AES_ENCRYPT(#{receiver_name}, ...), AES_ENCRYPT(#{tel1}, ...), AES_ENCRYPT(#{tel2}, ...), AES_ENCRYPT(#{zipcode}, ...), AES_ENCRYPT(#{shipping_address1}, ...), AES_ENCRYPT(#{shipping_address2}, ...) ) </foreach> </insert>
무거운 3가지 이유
01

useGeneratedKeys = true

generated key 후처리 비용이 추가된다. SIMPLE만 사용 가능한 경로를 강제한다.

02

<foreach> multi-row insert

row 수에 비례해 SQL 문자열이 커진다. SIMPLE에서 단일 실행 payload 피크가 직접 증가한다.

03

AES_ENCRYPT × 7컬럼

단순 값 바인딩보다 statement 텍스트가 훨씬 무거워진다. 같은 건수라도 row당 payload가 크다.

단순 건수가 아닌 row × payload 크기로 봐야 한다

08 결론

핵심 메시지

"chunking 하나가 아니라,
세션이 붙잡는 최대 작업량 상한 + flush + close
세 가지 조합이 피크 메모리를 낮췄다"
말하지 말 것
❌ "GC가 메모리를 바로 해제한다"
❌ "BATCH가 무조건 메모리 효율적"
❌ "clearCache()가 핵심"
❌ "flushStatements()에서 batch 시작"
정확한 표현
✓ "참조 생명주기를 짧게 만들어 GC가 회수 가능한 상태를 더 자주 만든다"
✓ "generated key 제약이 없고 flush 경계를 잘 설계했을 때"

한 줄 결론
BatchInsertExecutor의 핵심은 "대량 insert를 빠르게 했다"보다,
"MyBatis 세션이 내부적으로 붙잡는 batch 상태의 생명주기를
chunk 단위로 잘라 피크 메모리를 낮춘 것"에 있다.
