문제 상황 타임라인

출발점은 단순한 성능 개선이 아니라, 대용량 엑셀 업로드에서 반복되던 OOM을 구조적으로 줄이는 것이었습니다.

Legacy PHP
30,000건 업로드 시 OOM 발생
기존 PHP 물류사 시스템에서는 한 번에 30,000건 엑셀 발주 데이터를 업로드할 때 OOM이 발생했고, 운영에서는 메모리 증설로 우선 대응했습니다.
Spring Batch Goal
최소 50,000건까지 안정 처리
Spring Batch 전환의 목표는 단순 이관이 아니라, JVM Heap 1024MB 기준으로 최소 50,000건까지는 OOM 없이 업로드되는 상태를 만드는 것이었습니다.
AS-IS Batch Insert
Spring Batch에서도 30,000건 전후 OOM 재발
하지만 초기 bulk insert 구조로는 다시 30,000건 전후부터 OOM이 발생했고, 결국 insert 구간 메모리 사용 방식을 다시 봐야 했습니다.
TO-BE Result
BatchInsertExecutor 적용 후 60,000건 성공
개선 후에는 동일한 1024MB 메모리 조건에서 파일당 60,000건까지 업로드 가능했고, 70,000건부터 다시 실패 구간이 확인됐습니다.

04 원인 분석

OOM의 진짜 원인은
무엇인가

처음 가설

"엑셀 row 수가 많아서 읽는 과정에서 OOM이 났다"

파일 크기와 row 수 때문에 가장 먼저 떠올리기 쉬운 가설이지만, 실제 프로파일링 결과와는 달랐습니다.

검증 후 결론

문제는 읽기보다 쓰기 구간의 메모리 피크였습니다.

핵심은 row 수 자체가 아니라, MyBatis 세션이 SQL payload와 중간 상태를 얼마나 오래 붙잡고 있느냐였습니다.

발표용 핵심 문장
1. IntelliJ Profiler 기준으로 병목은 읽기가 아니라 쓰기에서 드러났습니다.
2. 엑셀 파일 단위 처리라 읽기 부하는 상대적으로 작았고, 쓰기 시점에는 chunk 단위 SQL payload와 세션 상태가 겹치며 피크가 형성됐습니다.
3. 따라서 OOM 원인은 "엑셀을 많이 읽어서"가 아니라 "쓰기 구간에서 중간 상태를 오래 붙잡는 구조"였습니다.
추가 참고
상세 분석 근거와 발표 방향은 첨부 예정인 딥다이트_기술공유_진행방향 자료를 추가로 참고하면 됩니다.

06 코드 구조 해부

BatchInsertExecutor
핵심 흐름

왜 만들었나

대량 insert 로직이 서비스마다 중복되기 시작했고, generated key 필요 여부에 따라 executor 전략도 달랐습니다.

그래서 chunk 단위 분할, executor 분기, 세션 생명주기 관리를 한 곳에 모은 공통 유틸로 분리했습니다.

간략한 장점

  • 호출부 단순화 : 서비스에서는 mapper와 list만 넘기면 됩니다.
  • 전략 일관성 : useGeneratedKeys 여부에 따른 분기를 공통화했습니다.
  • 메모리 제어 : chunk와 세션 경계를 명시적으로 나눠 피크를 낮춥니다.
ExecutorType executorType = useGeneratedKeys ? ExecutorType.SIMPLE : ExecutorType.BATCH; List<List<T>> batches = chunked(items, batchSize); for (List<T> batch : batches) { try (SqlSession s = factory.openSession(executorType)) { M mapper = s.getMapper(mapperClass); insertFn.accept(mapper, batch); if (executorType == ExecutorType.BATCH) { s.flushStatements(); s.clearCache(); } } }
프로세스 흐름 설명
executorType 결정
generated key 필요 여부에 따라 SIMPLE 또는 BATCH를 선택
items chunk 분할
전체 리스트를 처리 가능한 batch 단위로 자름
openSession()
chunk마다 새 세션을 열어 중간 상태의 생명주기를 짧게 가져감
mapper insert
이 시점부터 executor 내부 상태가 누적되기 시작
flush + clear
BATCH일 때만 batch 버퍼 실행 및 local cache 정리
session.close()
세션 종료로 chunk 단위 메모리 참조를 끊음
포인트 1: ExecutorType을 런타임에 결정합니다.
포인트 2: chunk마다 SqlSession을 새로 열고 닫습니다.
포인트 3: BATCH에서만 flushStatements()와 clearCache()를 묶습니다.
포인트 4: 현재 페이지의 프로세스 흐름 설명은 유지하고, 발표에서는 이 흐름만 짚어도 전체 의도가 전달됩니다.

08 API 역할 분리

flush · clearCache · close
역할이 다르다

flushStatements()

  • Statement.executeBatch() 실행
  • generated key 후처리
  • statement.close()
  • statementList.clear()
  • batchResultList.clear()

clearCache()

  • localCache.clear()
  • localOutputParameterCache.clear()
batch statement 버퍼를 직접 비우지 않습니다.

session.close()

  • transaction.close()
  • deferredLoads = null
  • localCache = null
  • 세션 생명주기 완전 종료
@Override public List<BatchResult> doFlushStatements(boolean isRollback) throws SQLException { ... stmt.executeBatch(); closeStatement(stmt); currentSql = null; statementList.clear(); batchResultList.clear(); }
@Override public List<BatchResult> doFlushStatements(boolean isRollback) { return Collections.emptyList(); }

10 결론

핵심 메시지

"chunking 하나가 아니라,
세션이 붙잡는 최대 작업량 상한 + flush + close
세 가지 조합이 피크 메모리를 낮췄다"
말하지 말 것
❌ "GC가 메모리를 바로 해제한다"
❌ "BATCH가 무조건 메모리 효율적"
❌ "clearCache()가 핵심"
❌ "flushStatements()에서 batch 시작"
정확한 표현
✓ "참조 생명주기를 짧게 만들어 GC가 회수 가능한 상태를 더 자주 만든다"
✓ "generated key 제약이 없고 flush 경계를 잘 설계했을 때"
이후 할 것
  • BatchInsertExecutorTest 작성
  • SIMPLE/BATCH 비교 실험 코드
  • 발표용 실험 그래프 생성
  • 테스트 로그 기반 타임라인 보강
한 줄 결론
BatchInsertExecutor의 핵심은 "대량 insert를 빠르게 했다"보다, "MyBatis 세션이 내부적으로 붙잡는 batch 상태의 생명주기를 chunk 단위로 잘라 피크 메모리를 낮춘 것"에 있습니다.
